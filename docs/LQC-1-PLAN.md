# LQC 第 1 輪:建置管線、測試網、模組化

**狀態:全案完成**(2026-09-06)。併入 `main` 待使用者實測後決定。

## 規劃前提的修正

初版規劃把「`content.js` 只有 179 行」當成不該拆分的理由,那是拿**改動幅度**當判準。
以專案整體方向重新評估後撤回該結論,理由如下。

**決定性論據:`publish/` 目前是 `cp` 出來的手動複本。** 沒有任何機制保證它與原始碼一致 ——
下一次改了 `content.js` 卻忘了複製,手動測的就是舊版,而且不會有任何訊號。
這個目錄天生就該是**建置產物**。一旦承認這點,bundler 就不是「為了模組化而多引入的工具」,
而是這個專案本來就缺的那一塊;而有了 bundler,MV3 不支援 ES module 的限制(初版核對 P3)自然解除,
「單檔還是多檔」不再需要在限制下權衡,可以純粹按內聚性決定。

因此本輪定案:**建立 `src/` + esbuild 建置管線,`publish/` 成為建置產物**。

## 目標結構

```
src/
  content.js      入口:組裝並註冊事件監聽
  link-target.js  連結偵測(composedPath 穿透、URL 可用性判定)
  hotkeys.js      按鍵分派(capture、修飾鍵、選取文字讓行)

tests/            vitest
manifest.json     來源;建置時複製進 publish/
publish/          建置產物
```

### 突變驗收推翻的一項前提(2026-09-06)

本輪規劃(與第一輪診斷)把 mouseout 的 `relatedTarget` 判斷列為「三個修復」之一,
突變驗收時還原該處**測試仍全綠**。依規則先懷疑測試,追根因後確認是**前提錯誤而非測試不足**:

DOM 規範保證 `mouseout` 之後必定緊接著對新元素派發 `mouseover`,因此 v1.3 清空紀錄後
會立刻被重新設定。無論在連結子元素間移動、移到連結本身、或移出到外部,兩版行為完全一致 ——
不存在可觀測的失敗情境,構造不出會紅的測試。

該判斷實際擋掉的是 `mouseout` 與 `mouseover` 之間 `hoveredLinkUrl` 為 null 的極短空窗
(按鍵剛好落在兩事件之間)。屬**防禦性強化,不是 bug 修復**。程式碼保留,已更正其註解與
測試名稱,並把它排除在必須轉紅的突變項目之外。

**連帶結論**:v1.4 真正修掉的可觀測缺陷只有兩個(capture 階段、composedPath)。
擴充原本「所有網站都沒反應」若非這兩者所致,就是擴充根本沒在執行 —— 這點仍待使用者實測確認。

### 實作中發現的規劃遺漏(2026-09-06 補入)

草擬作業 C 的測試時發現:提示膠囊的 shadow root 建為 `mode: 'closed'`,
**測試無法讀取其中的文字**,本作業定案的文案因此無法被斷言 —— 等於 C-2 的清單語意驗收缺一角。

處置:併入本作業,把 shadow root 改為 `mode: 'open'`。
評估過影響 —— 隔離性幾乎沒有損失:頁面 CSS 無論 open 或 closed 都無法穿透 shadow 邊界,
`closed` 只多擋了頁面 JS 的存取,而頁面 JS 本來就能取得宿主元素、也能直接移除它,
擋不擋得到內部並不構成實質防護。改為 open 換來可測試性,划算。

**驗收**:提示字串同時含「已存在」與「未重複加入」;shadow root 可由外部讀取;
兩者皆由作業 C 的測試斷言。

## 作業 C:測試網

### C-1 骨架與整合測試

**行為契約**

- vitest + jsdom,測試指令 `npm test`。
- 提供載入工具,把 **`publish/content.js` 建置產物**求值進新建的 jsdom 環境,回傳其 `window`/`document`,
  讓測試派發真實 DOM 事件。每個測試取得互相隔離的環境。
  - 測試對象是**產物**而非原始碼,如此才能同時驗證打包設定沒把事情弄壞。
  - `src/` 不得為了配合測試加入匯出、旗標或環境判斷分支。
- 替 jsdom 未實作的瀏覽器 API 提供可斷言、可指定失敗的替身,至少涵蓋
  `navigator.clipboard.writeText` 與 `document.execCommand`。
- **暫定**:jsdom 對 `document.elementFromPoint` 支援可能不足;執行端實測不可用時可改用替身,
  並在回報寫明理由。

**驗收**:`npm test` 結束碼 0;煙霧測試 —— 對連結派發 mouseover 後派發 Cmd/Ctrl+C,替身剪貼簿收到該網址。

### C-2 行為測試套件

**行為契約** —— 一律透過派發真實 DOM 事件驗證,不得直接呼叫內部函式。至少涵蓋:

1. **連結偵測**:一般 `<a href>`;**Shadow DOM 內**的連結(對應 composedPath 修復);
   連結子元素之間移動**不清空**紀錄(對應 relatedTarget 修復);移出到外部元素**須**清空;
   `javascript:` / `about:` / `data:` 不採用。
2. **按鍵分派**:頁面於捕獲階段之後 `stopPropagation()` 時複製仍成立(對應 capture 修復);
   有選取文字時 Cmd/Ctrl+C 不被攔截;`event.repeat` 不重複觸發;未指向連結時無動作;
   Cmd 與 Opt 同按時不觸發任一模式。
3. **清單語意**:三個不同連結累加為三行且順序一致;重複連結筆數不變且提示含「已存在」「未重複加入」;
   Cmd+C 覆蓋複製會**重置**清單;空清單第一次加入顯示「共 1 筆」。
4. **剪貼簿**:`writeText` 失敗時走 `execCommand` 且仍顯示成功提示;兩者皆失敗顯示錯誤提示。

**驗收**

- 全套綠。
- **突變驗收(必做)**:逐一還原下列三處為 v1.3 寫法,每處都必須有測試由綠轉紅,記錄對應測試名稱:
  keydown 的 capture 旗標、連結搜尋改回 `event.target.closest`、mouseout 移除 `relatedTarget` 判斷。
  **某處還原後仍全綠時,先懷疑自己的測試,不要懷疑突變。**
- 回報須附完整測試輸出與突變驗收結果表,不接受口頭摘要。

1. **寫閘門時要問「接下來幾段作業會不會讓這條檢查必然失敗」。** 針對當前結構寫死的檢查,

4. **每條新檢查都必須做一次突變確認,且突變要改在「來源」而非「產物」。**

### 我最沒把握的地方(給體檢方的優先順序,但不要只看這幾處)

1. **`anchorAtPoint` 是收尾階段才補的新程式碼**(`src/link-target.js`)。它逐層往
   shadow root 遞迴查詢,但測試裡 `shadowRoot.elementFromPoint` 是我手工塞的替身
   —— jsdom 沒有實作。**真實 Chrome 上巢狀 shadow root 的行為完全沒驗過**,
   尤其是 `mode: 'closed'` 的 shadow root(`elementFromPoint` 取不到 `shadowRoot`,
   迴圈會直接跳出)。這是本輪風險最高的一段。

2. **兩個獨立稽核在終檢時找到 8 項實質問題,其中 3 項是假通過的測試、1 項是我漏抄契約。**
   這個比例說明我自己的檢查有系統性盲點:我對「三個修復」做了突變驗收,卻沒有對
   **測試網本身**做突變。體檢方應假設仍有未發現的假通過測試,
   優先對 `tests/` 的每一條斷言做一次突變。

3. **`scripts/build.mjs` 的 watch 模式**。我補了 `fs.watch` 監看 manifest 與圖示,
   但 `verify-build.sh` 只確認它「啟動後不會立刻崩潰」,**沒有任何測試驗證它真的會重新複製**。
   `watch(ICONS_SRC, { recursive: true })` 在 Linux 上的支援也與 macOS 不同。

4. **`src/toast.js` 的計時器與宿主元素狀態**。快速連續觸發多次提示時,
   `toastTimer` 的清除與 `toastHost.isConnected` 的判斷有沒有競態,沒有測試涵蓋。

5. **jsdom 與真實 Chrome 的落差**是整個測試網的天花板。31 條測試證明的是
   「程式碼在 jsdom 中的行為符合預期」,不能證明擴充在 Chrome 裡會動。
