# LQC 第 1 輪:建置管線、測試網、模組化

## 規劃前提的修正

初版規劃把「`content.js` 只有 179 行」當成不該拆分的理由,那是拿**改動幅度**當判準。
以專案整體方向重新評估後撤回該結論,理由如下。

**決定性論據:`publish/` 目前是 `cp` 出來的手動複本。** 沒有任何機制保證它與原始碼一致 ——
下一次改了 `content.js` 卻忘了複製,手動測的就是舊版,而且不會有任何訊號。
這個目錄天生就該是**建置產物**。一旦承認這點,bundler 就不是「為了模組化而多引入的工具」,
而是這個專案本來就缺的那一塊;而有了 bundler,MV3 不支援 ES module 的限制(初版核對 P3)自然解除,
「單檔還是多檔」不再需要在限制下權衡,可以純粹按內聚性決定。

因此本輪定案:**建立 `src/` + esbuild 建置管線,`publish/` 成為建置產物**。

## 目標結構

```
src/
  content.js      入口:組裝並註冊事件監聽
  link-target.js  連結偵測(composedPath 穿透、URL 可用性判定)
  hotkeys.js      按鍵分派(capture、修飾鍵、選取文字讓行)
  clipboard.js    剪貼簿寫入與 execCommand fallback
  toast.js        Shadow DOM 提示 UI
  state.js        游標所指連結、累加清單
tests/            vitest
manifest.json     來源;建置時複製進 publish/
publish/          建置產物
```

## 核對結論(沿用)

- 專案原本完全沒有測試、`package.json` 或建置流程;本機 Node v22.14.0 / npm 10.9.2 可用。
- v1.4 修掉的三個 bug(keydown 未用 capture、Shadow DOM 的 event retarget、mouseout 誤清紀錄)
  **全部位於事件接線層**,沒有一個是純函式邏輯錯誤。
  → 測試策略的硬性要求:**必須有一層測試是對建置產物派發真實 DOM 事件**。
  只測抽出來的純函式,這三個 bug 一個都抓不到。模組拆分後尤其危險,因為單元測試會全綠而擴充是壞的。

## 作業 A:建置管線(純搬移)

**行為契約**

- 建立 `package.json`,以 esbuild 將 `src/content.js` 打包為 `publish/content.js`
  (IIFE 格式,非 ES module —— MV3 content script 是傳統腳本)。
- 建置同時把 `manifest.json` 複製進 `publish/`,使 `publish/` 隨時是可直接「載入未封裝項目」的完整目錄。
- 提供 `npm run build` 與監看模式。
- **本作業不得改動任何一行邏輯**:`src/content.js` 就是現行 `content.js` 原封搬過去。
  拆分留給作業 D。
- 根目錄的 `content.js` 移除(改由 `src/` 持有),`manifest.json` 留在根目錄當來源。

**驗收**

- `npm run build` 結束碼 0,產出 `publish/content.js` 與 `publish/manifest.json`。
- `node --check publish/content.js` 通過。
- 產物與搬移前的 `content.js` **行為等價**:去除打包外殼後的敘述序列一致,無新增或遺漏的監聽器。
- `publish/` **已從 `.gitignore` 移除並納入版控**,產物與 `src/` 同一個 commit 內一致。

## 作業 C:測試網

### C-1 骨架與整合測試

**行為契約**

- vitest + jsdom,測試指令 `npm test`。
- 提供載入工具,把 **`publish/content.js` 建置產物**求值進新建的 jsdom 環境,回傳其 `window`/`document`,
  讓測試派發真實 DOM 事件。每個測試取得互相隔離的環境。
  - 測試對象是**產物**而非原始碼,如此才能同時驗證打包設定沒把事情弄壞。
  - `src/` 不得為了配合測試加入匯出、旗標或環境判斷分支。
- 替 jsdom 未實作的瀏覽器 API 提供可斷言、可指定失敗的替身,至少涵蓋
  `navigator.clipboard.writeText` 與 `document.execCommand`。
- **暫定**:jsdom 對 `document.elementFromPoint` 支援可能不足;執行端實測不可用時可改用替身,
  並在回報寫明理由。

**驗收**:`npm test` 結束碼 0;煙霧測試 —— 對連結派發 mouseover 後派發 Cmd/Ctrl+C,替身剪貼簿收到該網址。

### C-2 行為測試套件

**行為契約** —— 一律透過派發真實 DOM 事件驗證,不得直接呼叫內部函式。至少涵蓋:

1. **連結偵測**:一般 `<a href>`;**Shadow DOM 內**的連結(對應 composedPath 修復);
   連結子元素之間移動**不清空**紀錄(對應 relatedTarget 修復);移出到外部元素**須**清空;
   `javascript:` / `about:` / `data:` 不採用。
2. **按鍵分派**:頁面於捕獲階段之後 `stopPropagation()` 時複製仍成立(對應 capture 修復);
   有選取文字時 Cmd/Ctrl+C 不被攔截;`event.repeat` 不重複觸發;未指向連結時無動作;
   Cmd 與 Opt 同按時不觸發任一模式。
3. **清單語意**:三個不同連結累加為三行且順序一致;重複連結筆數不變且提示含「已存在」「未重複加入」;
   Cmd+C 覆蓋複製會**重置**清單;空清單第一次加入顯示「共 1 筆」。
4. **剪貼簿**:`writeText` 失敗時走 `execCommand` 且仍顯示成功提示;兩者皆失敗顯示錯誤提示。

**驗收**

- 全套綠。
- **突變驗收(必做)**:逐一還原下列三處為 v1.3 寫法,每處都必須有測試由綠轉紅,記錄對應測試名稱:
  keydown 的 capture 旗標、連結搜尋改回 `event.target.closest`、mouseout 移除 `relatedTarget` 判斷。
  **某處還原後仍全綠時,先懷疑自己的測試,不要懷疑突變。**
- 回報須附完整測試輸出與突變驗收結果表,不接受口頭摘要。

## 作業 E:專案成熟度(已定案全數納入)

### E-1 產物版控與 CI

**行為契約**
- `publish/` 納入版控(`.gitignore` 移除該項),使 clone 後可直接「載入未封裝項目」,無需安裝 Node。
- GitHub Actions 於 push 與 PR 觸發:`npm ci` → `npm run build` → `npm test`。
- CI 必須額外驗證**產物是最新的**:重新建置後比對工作區,`publish/` 若出現任何 diff 即失敗。
  這是產物進版控唯一的防線 —— 沒有它,不同步風險就完全沒人擋。

**驗收**:CI 在 GitHub 上實際跑綠;蓄意改一行 `src/` 但不重新建置後推分支,CI 必須紅。

### E-2 擴充圖示

**行為契約**
- 提供 16 / 32 / 48 / 128 四種尺寸 PNG,於 `manifest.json` 的 `icons` 宣告,並由建置複製進 `publish/`。
- 視覺概念:連結與複製的意象,單色扁平,深淺背景下皆可辨識。
- **暫定**:產生工具未定(Pillow 是否可用需實測)。執行端可自行選擇可行方案,於回報寫明。

**驗收**:四個尺寸檔案存在且尺寸正確;`chrome://extensions` 載入後顯示圖示而非預設灰塊。

### E-3 文件與清理(Claude 親寫文件部分)

**行為契約**
- 移除 `ChromeExtension_CopyUrl.sln`(Rider 殘留,對 Chrome 擴充無用途)。
- `README.md` 加強:安裝改指向 `publish/`(強調 clone 後可直接載入)、開發者章節(建置與測試指令)、
  專案結構說明、按鍵行為表、已知限制。
- 新增 `CLAUDE.md`:專案入口地圖,指向 `docs/` 與 `src/` 各模組職責。
- 新增 `docs/SPEC.md` 現況規格:按鍵契約、連結偵測規則、清單語意、剪貼簿 fallback 策略、
  提示文案清單、MV3 限制與其因應。**記錄現況,不記錄變更史**。
- 本輪 PLAN 於收尾時移入 `docs/archive/`。

**驗收**:`.sln` 不存在;README 的建置與測試指令實際可執行;`docs/SPEC.md` 所述行為與作業 C 的測試逐條對得上。

## 規劃完成後複檢

- **與既有設計的衝突(複檢抓到)**:使用者定案「產物進版控」與作業 A 原訂驗收「`git status` 中
  `publish/` 不出現」直接矛盾。**已修正 A 的驗收**為產物須納入版控。連帶:`.gitignore` 目前含
  `publish/` 一行,須於作業 A 移除,不能留到 E-1 —— 否則 A 完成時產物根本進不了 commit。
- 作業 A 移除根目錄 `content.js`,README 安裝說明需同步更新,已列入 E-3。
  GitHub 上現有的 v1.4 commit 不受影響。
- **批次間衝突**:B 改動的文案被 C-2 斷言 → 順序必須 B 先於 C(已定)。
  D 改 `src/` 而 C 測 `publish/` 產物 → D 每次驗收前需重新 build,已在 D 的驗收隱含要求
  (`npm test` 前必須 `npm run build`;執行端應把 build 掛進 test 指令的前置步驟)。
- **什麼算一個 / 分母為零**:清單筆數為陣列元素個數,空清單第一次加入顯示「共 1 筆」,已列入 C-2 驗收。
- **破壞性判準**:作業 A 會刪除根目錄 `content.js`。該檔已在 GitHub main 上有紀錄,可還原,非不可逆。
  本地 `content.js.bak` 保留不刪。
- **單向閘門**:無。
- **移除類的依賴方**:根目錄 `content.js` 的依賴方為 `manifest.json` 的 `js` 陣列(改由建置產出)、
  README 安裝說明、`publish/` 的複製來源 —— 三者皆已在契約中交代。
- **升級路徑**:擴充無持久化狀態,使用者重新載入即可。

- **E-1 的順序**:CI 驗證產物新鮮度,必須在 D 完成、目錄結構定案後才建立,否則會反覆因結構調整而紅。
- **圖示與建置的交互**:E-2 新增的 PNG 需由建置複製進 `publish/`,亦即 E-2 會回頭改動作業 A 的建置腳本;
  已在 E-2 契約中明寫,避免執行端只放檔案卻沒接進建置。

複檢完成(第二輪),已修正一項衝突、補齊兩項順序相依。
